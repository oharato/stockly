# テスト戦略方針書 (Testing Strategy & Testing Trophy)

本ドキュメントは、**Stockly** におけるテスト方針、設計思想、および具体的な実装規約を定義したドキュメントです。

---

## 1. モダンなフロントエンドテスト戦略：テストピラミッド vs テストトロフィー

### 1.1 従来の「テストピラミッド (Test Pyramid)」の限界

Mike Cohn が提唱した「テストピラミッド」は、ピラミッドの底辺に大量の単体テスト（Unit）を配置し、中間に結合テスト（Integration）、頂点に少数の E2E テストを配置するモデルでした。

```
     /  E2E  \       (少数)
    /  結合   \      (中量)
   /  単体テスト \   (大量)
  ───────────────
```

しかし、モダンなフロントエンド開発（TypeScript + Svelte 5 + Component-Driven UI）において、テストピラミッドには以下の課題が生じました：

1. **静的型チェックの進化**: TypeScript がプロパティの有無や型不整合をコンパイル時に検知するため、従来の単体テストで書いていた単純な型確認・nullチェックテストの存在価値が薄れた。
2. **過度なモック化（Mocking）による弊害**: 単体テストで各関数や子コンポーネントをモックしすぎると、「テストは通るのに組み合わさると動かない」という現象が頻発する。
3. **実装詳細への結合**: 内部状態（state）や内部メソッドを直接検証する単体テストは、リファクタリング時にテストが壊れやすく、開発スピードを低下させる（リファクタリング耐性の低さ）。

---

### 1.2 「テストトロフィー (The Testing Trophy)」の採用

Kent C. Dodds（Testing Library 作者）が提唱した **「テストトロフィー」** は、投資対効果（ROI）と信頼性（Confidence）の観点から、**結合テスト（Integration）を最も分厚く配置** するモダンなテストモデルです。

```
        /   E2E   \       End-to-End: ユーザーの重要クリティカルパスを検証
       /───────────\
      │ 結合テスト  │     Integration: ★最重要・最も分厚い層
      │(Integration)│     コンポーネント + ストア + 通信のユーザー行動テスト
       \───────────/
        \ 単体(Unit)/     Unit: 複雑な純粋関数・計算ロジック・バリデーション
         \─────────/
          [ Static ]      Static Analysis: 型検査 (TypeScript), Lint/Format (Vite+ vp check)
```

> **"Write tests. Not too many. Mostly integration."**
> — _Kent C. Dodds_
>
> **"The more your tests resemble the way your software is used, the more confidence they can give you."**
> （テストがソフトウェアの実際の使われ方に似ていればいるほど、自信を持てる）

## 2. Stockly における 4 層のテスト配置

| レイヤー                              | ツール / 実行方法                                    | 対象・責務                                 | 特徴・検証内容                                                                                                                                                  |
| ------------------------------------- | ---------------------------------------------------- | ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1. Static (静的検査)**              | `vp check` (tsgolint + Oxlint + Oxfmt)               | 全コードベース                             | ・構文エラー、未定義変数、型の完全性<br>・**800ms 未満** で瞬時に実行                                                                                           |
| **2. Unit (単体テスト)**              | `vp test` (内蔵 Vitest)                              | 純粋ロジック、ユーティリティ、スキーマ     | ・日付フォーマット / グループ化計算<br>・Zod バリデーション境界値（文字数制限、空文字）<br>・ストリーク連続日数計算                                             |

## 3. テスト実装の原則 (Guiding Principles)

1. **実装の詳細（Implementation Details）をテストしない**:
   - プライベートな変数や内部メソッドの呼び出し回数をモックで検証しない。
   - 「ユーザーが入力した」「ボタンを押した」「結果が返ってきた」「UIが更新された」という **振る舞い（Behavior）** を検証する。
2. **高速性とリファクタリング耐性**:
   - `vp test` による内蔵 Vitest でミリ秒単位（数百ms以内）で全テストが完了すること。
   - 内部実装を Svelte 5 の Runes でリファクタリングしても、外部からの入出力仕様が変わらなければテストが壊れないこと。
3. **継続的検証**:
   - コミット前必須チェック: `vp check` ＋ `vp test --run`。

## 4. モダン E2E テストの現状分析：Playwright・Vitest Browser Mode・API E2E の役割分担

### 4.1 Playwright の現状とメリット・デメリット

現在、ヘッドレスブラウザ自動化ツールの分野では **Playwright がデファクトスタンダード（業界標準）** となっています（Cypress や Selenium は速度やアーキテクチャの制約からシェアを落としています）。

| 観点                   | Playwright の特徴                                                                                                                                                                                                      |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **圧倒的な強み**       | ・実ブラウザ（Chromium, WebKit, Firefox）での完全な忠実度<br>・Auto-wait（DOMの描画待ち）によるフレーキー（不安定）テストの撲滅<br>・Trace Viewer（実行時のDOM・通信・スクリーンショットをタイムラインで再生デバッグ） |
| **課題（なぜ重いか）** | ・ブラウザバイナリのダウンロード（数百MB〜GB規模）が必要<br>・ヘッドレスブラウザ起動のオーバーヘッドにより、数秒〜数十秒の実行時間がかかる<br>・開発中のローカルTDD（ミリ秒で回すループ）を阻害しやすい                |

### 4.2 最新フロントエンドにおける「E2E の役割の細分化」

近年のテストエコシステムでは、**「すべてを Playwright で重く回す」のをやめ、3つのレイヤーに賢く役割分担する** のが主流です：

1. **API-Level E2E（高速 E2E - 今回採用）**:
   - **実行基盤**: `vp test` (Vitest)
   - **速度**: **200〜300ms**
   - **役割**: ブラウザを介さずに、実際の HTTP リクエストでフロント ➔ バックエンド ➔ データベース（D1）の全パスを貫通検証。DB永続化やビジネスロジックの破壊を日常のコミット時にミリ秒で検知。
2. **Vitest Browser Mode（コンポーネント結合テストの新潮流）**:
   - **実行基盤**: Vitest 内蔵ブラウザモード (`@vitest/browser`)
   - **役割**: Vite の HMR を使い、実ブラウザ内でコンポーネントを高速マウント。jsdom では検知できない CSS、レイアウト、実ブラウザ固有のイベントをテスト。
3. **Playwright（高信頼 E2E - ローカル & 本番の2系統）**:
   - **実行基盤**: `@playwright/test@1.63.0`
   - **速度**: 数秒〜十数秒
   - **役割**:
     - `test:e2e:local`: ローカル開発サーバー（Vite 5173 + API 8787）を自動起動し、投稿・検索・削除・タブ遷移のクリティカルパスを検証。
     - `test:e2e:prod`: 本番環境（`https://stockly.ohchans.com`）に対し、高速タイピング時の 429 レートリミット耐性やタグ絞り込み、Service Worker キャッシュ動作を検証。

### 4.3 Stockly における運用方針

- **日常の開発サイクル (Inner Loop)**:
  - `vp check`（型・リント・フォーマット一括）+ `vp test --run`（Vitest Unit + Integration）で **1〜2秒以内に全件パス** させる。
- **結合・リリース前サイクル (Outer Loop)**:
  - UI や API の挙動変更時および本番デプロイ前には、`pnpm test:e2e:local`（および Access OFF 状態での `pnpm test:e2e:prod`）を実行し、実ブラウザ上での耐久性・表示崩れ・ネットワーク耐性を確認する。

## 5. D1 テスト基盤の設計と技術選定

### 5.1 旧課題：手書きモック（クエリ文字列判定）の限界

初期実装では、SQL 文字列の `query.includes(...)` による手書きモックを使用していましたが、以下の重大な問題がありました：

1. **追随コストの肥大化**: SQL のカラム追加や JOIN、WHERE 句の微修正を行うたびにモック側の文字列判定を手動修正しなければならない。
2. **SQL 構文・制約の検証不能**: テーブル定義や外部キー制約（Foreign Key）を無視するため、親レコードが存在しない不正なデータ挿入をパスしてしまう。
